# Fase 1.4 — Achados Infra/IO

Data: 2026-06-04

Auditoria de corretude (precisão/robustez) e de implementação (bugs de contrato) da camada
de **infraestrutura de I/O**: `infrastructure/io/image_io.py` (PNG via cv2 + FNI textual de
floats que faz fronteira com o binário C) e `infrastructure/utils.py` (normalização, média e

corrompidos silenciosamente entre estágios. Esta fase também produz o **mapa sistemático de
call-sites de `save_image`** (tabela obrigatória abaixo), classificando cada um como
visualização-apenas (ok) ou dado-consumido-depois (achado/cross-ref).

Cada achado cita `arquivo:linha` reais (verificados no branch `nova_iteracao`). Status é
"suspeita" salvo quando o código por si só prova o defeito ("confirmado (por inspeção)").
Comportamentos numpy/cv2/formatação foram confirmados com one-liners (registrados na
evidência). Achados de IO já registrados em fases anteriores são **cross-referenciados, não
duplicados**: MF-12 (médias quantizadas a uint8 antes da medida de foco), PS-07 (entrada do
PS quantizada a 8 bits via `sMos.png`; `sMos.fni` ignorado), INT-03 (NaN textual no FNI —
backstop no C), INT-06 (`hAvg.png` uint8 vs unidades de altura).

## IO-01: `convert_image_array_to_fni` grava `%.7e` — trunca float64 (zMos/alturas/confiança) a ~7-8 dígitos significativos

- **Localização:** `src/hybrid_stereo_method/infrastructure/io/image_io.py:173,176`
- **Tipo:** implementação
- **Severidade:** baixo
- **Status:** confirmado (por inspeção) — o truncamento é determinístico pelo formato

**Descrição:** O writer FNI formata cada amostra com `f"{...:+.7e}"` (`image_io.py:173` para
NC=1, `:176` para NC>1), ou seja **7 casas após o ponto** ⇒ 8 dígitos significativos. Para
**float32** isso é suficiente: o round-trip `np.float32(float(f"{v:+.7e}"))` é **exato** (a
float32 carrega ~7 dígitos significativos; 8 cobrem com folga — verificado para `0.1`, `π`,
`1.2345678e±05`). Porém os dados do multifocus passados a este writer são **float64**:
`zMos.fni` (`multifocus/main.py:155`, `zMos = np.zeros((h,w))` ⇒ float64,
`mosaic.py:39`) e `zMos_with_confidence.fni` (`main.py:159-161`, `np.stack` de dois float64).
Estes são alturas físicas em unidades de `z_foc` e a confiança normalizada. O `%.7e` **trunca**
float64 a ~7 dígitos significativos (verificado: `0.123456789012345` → `+1.2345679e-01` →
round-trip `0.12345679`, perde dígitos a partir do 8º). Como esses valores alimentam os hints
da integração C (consumido em `gus_integrate_recursive.c` via `tire_read_fni_file`), há perda
de precisão de ~1e-7 relativo no alvo de hints. O impacto numérico é pequeno (hints já entram
com `hints_weight` baixo e em escala incomensurável — ver INT-04), daí severidade **baixo**.
A justificativa decisiva para a baixa severidade é que **ambos os consumidores são float32**:
`read_fni_to_image_array` aloca `float32` (`image_io.py:223`) e o integrador C armazena em
`float_image_t` de 32 bits — portanto a perda de `%.7e` (~1e-7 relativo, na ordem do epsilon
de float32 1.19e-7) está **abaixo do que os consumidores representam**; a precisão float64 da
fonte se perde na fronteira float32 independentemente do formato do writer. Ainda assim, o
contrato do writer **não preserva** float64 e isso não está documentado.

**Evidência:** `f"{image_array[y, x]:+.7e}"` (`image_io.py:173`); `f"{v:+.7e}"` (`:176`).
Round-trip verificado por one-liner: float32 exato; float64 `0.123456789012345` →
`0.12345679` (perde do 8º dígito). zMos é float64 (`mosaic.py:39`); `zMos.fni`/
`zMos_with_confidence.fni` escritos sem cópia/cast para precisão maior (`main.py:155,159-161`).

**Sugestão de correção:** usar `%.17g` (round-trip exato de float64) ou, no mínimo, `%.15e`
para os FNIs que carregam dados físicos (zMos/confiança); documentar a precisão do formato.

**Correção aplicada:** `4e1ad88` (2026-06-06) — ambos os format specs `:+.7e` substituídos
por `:+.16e` com comentário IO-01 inline. O arquivo FNI passa a carregar a precisão do float64
fonte; float32 consumers (reader Python + integrador C) continuam corretos. Teste:
`tests/test_fni_roundtrip.py::test_roundtrip_preserves_float64_precision`. **Status: corrigido.**

## IO-02: `read_fni_to_image_array` deixa pixels ausentes silenciosamente em 0 (sem verificação de completude)

- **Localização:** `src/hybrid_stereo_method/infrastructure/io/image_io.py:222-243`
- **Tipo:** implementação
- **Severidade:** médio
- **Status:** confirmado (por inspeção) — a ausência de verificação é estrutural

**Descrição:** O reader aloca o array de saída com `np.zeros((ny,nx[,nc]), dtype=np.float32)`
(`image_io.py:222-225`) e o preenche pixel-a-pixel a partir das linhas de dados
(`:227-241`). **Não há verificação de que todos os `ny*nx` pixels foram efetivamente
escritos.** Se o FNI estiver incompleto (truncado, com linhas faltando, ou com índices `(x,y)`
fora de ordem/ausentes), os pixels não cobertos permanecem **0** silenciosamente — sem
exceção, sem aviso. Para o caminho `-end-Z.fni` (resultado da integração relido em
`integrate.py`), um arquivo truncado produziria um mapa de altura com regiões zeradas
interpretadas como altura válida 0, contaminando o resultado científico sem qualquer sinal.
Combina-se com o risco de fallback silencioso de INT-02 (que pode devolver o chute inicial):
ambos compartilham a filosofia "preencher silenciosamente em vez de falhar". Além disso, o
valor de preenchimento **0** é indistinguível de uma altura/slope/confiança legítima igual a
0, então nem uma inspeção posterior do array revelaria o problema.

**Evidência:** `image_array = np.zeros(...)` (`image_io.py:222-225`); o loop `for line in
lines` (`:227`) só atribui aos pixels presentes; nenhuma contagem de pixels escritos nem
comparação com `ny*nx` ao final; `return image_array` (`:243`) incondicional. Contraste com
o C, que ao **escrever** cobre todos os pixels em ordem row-major (verificado em
`03-integration.md`), mas o reader Python não impõe reciprocidade na **leitura**.

**Sugestão de correção:** rastrear um contador/máscara de pixels preenchidos e levantar
`ValueError` se `count != ny*nx` ao final; ou inicializar com NaN para tornar ausências
detectáveis a jusante.

**Correção aplicada:** `ff67af4` (2026-06-06) — `filled = np.zeros((ny,nx), dtype=bool)` após a
alocação; `filled[y,x] = True` em cada pixel escrito; `if not filled.all(): raise
ValueError("FNI file incomplete: N of M pixels missing (IO-02)")` antes do `return`. Teste:
`tests/test_fni_roundtrip.py::test_truncated_fni_raises`. **Status: corrigido.**

## IO-03: parser FNI pula silenciosamente linhas de dados com menos de `2+nc` campos

- **Localização:** `src/hybrid_stereo_method/infrastructure/io/image_io.py:231-232`
- **Tipo:** implementação
- **Severidade:** baixo
- **Status:** confirmado (por inspeção)

**Descrição:** Dentro do loop de dados, `if len(parts) < 2 + nc: continue` (`image_io.py:231-232`)
descarta **silenciosamente** qualquer linha que tenha menos de `2+nc` campos (esperado: `x y
v1..vnc`). A intenção plausível é tolerar linhas-lixo, mas o efeito é que uma linha de pixel
**malformada/truncada** (ex.: um valor faltando por escrita parcial) é pulada sem aviso,
deixando aquele pixel no valor de preenchimento 0 (ver IO-02). Note a assimetria com a linha
seguinte: se a linha tiver `>= 2+nc` campos mas `len(values) != nc` após o slice `parts[2:]`,
aí sim levanta `ValueError` (`:236-237`). Ou seja, **falta de campos** é silenciada, mas
**excesso** é erro — um tratamento inconsistente do mesmo tipo de corrupção. (Após o `continue`
para linhas curtas, `len(values) = len(parts) - 2 >= nc` sempre, logo o raise só dispara para
excesso de campos.) O parser também pula corretamente cabeçalho/rodapé/metadados via
`startswith("begin")/("end")` e `"=" in line` (`:228`), o que cobre o caso "linha com `=` no
meio dos dados" do checklist: tal linha seria interpretada como metadado e **pulada** dos
dados (benigno se for de fato metadado, mas mascararia uma linha de dados que contivesse `=`
por corrupção — improvável dado o formato numérico).

**Evidência:** `if len(parts) < 2 + nc: continue` (`image_io.py:231-232`) vs
`if len(values) != nc: raise ValueError(...)` (`:236-237`) — silencia falta, erra no resto.
`"=" in line` no filtro de skip (`:228`) trata qualquer linha de dados com `=` como metadado.

**Sugestão de correção:** unificar o tratamento: linha de dados malformada deve levantar (ou
ao menos logar um aviso), não ser pulada silenciosamente.

**Correção aplicada:** `ff67af4` (2026-06-06) — `continue` substituído por `raise
ValueError("Malformed FNI data line ...")`. A guarda de "linha de dados" usa
`parts[0].isdigit()`: somente linhas cujo primeiro token é um inteiro não-negativo são
tratadas como dados e têm o número de campos verificado; linhas sem primeiro token dígito
(possíveis comentários de C tools) continuam a ser puladas. Assimetria falta/excesso
resolvida: ambos agora levantam. Teste:
`tests/test_fni_roundtrip.py::test_malformed_short_line_raises`. Compatibilidade C confirmada:
`test_integration_units.py` (não-slow) 17/17 passed. **Status: corrigido.**

## IO-04: `save_image(..., normalize=True)` (default) quantiza e min-max-estica arrays float salvos como PNG consumidos a jusante

- **Localização:** `src/hybrid_stereo_method/infrastructure/io/image_io.py:137-142`; call-sites na tabela abaixo
- **Tipo:** implementação
- **Severidade:** médio
- **Status:** confirmado (por inspeção) — o cast uint8 é incondicional; consumo a jusante varia por call-site
- **Resolução (composição, 45cbf57):** os dois call-sites de "achado (consumido)" tiveram seus caminhos de dados fechados por composição: `average_{zf}.png` pelo MF-12 (médias float em memória via `filtered_images`); `sMos.png` por PS-07 (mosaicos float em memória via `sMos_images`). Os PNGs continuam sendo gravados para visualização, mas nenhum dado científico passa por eles no pipeline híbrido. Os demais call-sites são todos ok (visualização).

**Descrição:** `save_image` **sempre** grava uint8: no ramo `normalize=True` (default) faz
`cv2.normalize(img, None, 0, 255, NORM_MINMAX).astype(np.uint8)` (`image_io.py:138`); no ramo
`normalize=False` faz `np.clip(img,0,255).astype(np.uint8)` (`:140`). Logo **todo** array
float que passa por `save_image` é quantizado a 8 bits, e no ramo default sofre ainda um
**min-max stretch destrutivo** (perde a escala absoluta e o offset). `read_image` usa
`IMREAD_UNCHANGED` (`:90`), que **preserva** profundidade na leitura (um PNG 16-bit voltaria
uint16), mas o writer nunca produz 16-bit — a assimetria leitura/escrita significa que
qualquer round-trip float→PNG→float perde precisão e (no default) escala. A tabela de
call-sites abaixo classifica cada uso. Os achados de dado-consumido-depois já cobertos por

**Evidência:** `img_out = cv2.normalize(...).astype(np.uint8)` (`image_io.py:138`);
`img_out = np.clip(img,0,255).astype(np.uint8)` (`:140`) — ambos os ramos terminam em uint8.
`read_image` com `IMREAD_UNCHANGED` (`:90`) preserva profundidade na leitura mas o writer não.
Verificado: `cv2.normalize(float64, NORM_MINMAX)` devolve float64 e o `.astype(uint8)`
posterior quantiza.

**Sugestão de correção:** para dados consumidos a jusante, gravar FNI (já existe) e usar PNG
só para visualização; se PNG for necessário como dado, suportar 16-bit e `normalize=False`.

## IO-05: médias por plano focal salvas com `normalize=True` — cada `average_{zf}.png` é min-max-esticado independentemente, quebrando a comparabilidade entre planos

- **Localização:** `src/hybrid_stereo_method/hybrid/main.py:111`; relido em `src/hybrid_stereo_method/multifocus/main.py:96`
- **Tipo:** conceitual
- **Severidade:** alto
- **Status:** suspeita (decide: teste sintético do multifocus em hybrid mode, Task 11/12)
- **Resolução (composição, 45cbf57):** o caminho de dados das médias foi fechado por MF-12 (médias float em memória via `filtered_images`); com PS-07 também fechado, nenhum dado científico do pipeline híbrido passa por `save_image` antes de ser consumido. IO-05 (stretch per-plano) afeta apenas a visualização dos PNGs `average_{zf}.png`, não o resultado científico.

**Descrição:** No fluxo híbrido, a média de cada plano focal `zf` é salva com
`save_image(..., f"average_{zf_dir}.png", average_image)` **sem** `normalize=False`
(`hybrid/main.py:111`), logo cada arquivo é **min-max esticado independentemente** para
[0,255] (`image_io.py:138`). Em seguida o multifocus relê exatamente esses arquivos como
`filtered_dir` (`multifocus/main.py:96`) e calcula a medida de foco **comparando os planos
entre si** (argmax ao longo do eixo `zf` em `compute_argmax_fuzzy`). A medida de foco
(Laplaciano/Fourier/wavelet) depende de **contraste relativo entre planos**; ao normalizar
cada plano por seu próprio min/max, planos com pouca energia (desfocados, baixo contraste) são
**ampliados** ao mesmo intervalo [0,255] dos planos nítidos, **artificialmente igualando** a
escala de intensidade entre planos. Isso pode deslocar o argmax de foco para o plano errado,
corrompendo o `iSel` e portanto todo o mapa de profundidade e os mosaicos derivados. É distinto
de MF-12 (que trata da **quantização a uint8** da média): aqui o problema é a **normalização
per-plano** que destrói a relação de intensidade inter-plano antes mesmo da quantização.
Contraste deliberado: o mesmo arquivo principal **sabe** desativar a normalização quando ela
quebra relações cross-imagem (os mosaicos por luz usam `normalize=False` com comentário
explícito, `hybrid/main.py:157-160`), mas a média por-zf **não** recebe o mesmo cuidado.

**Evidência:** `save_image(average_image_path, f"average_{zf_dir}.png", average_image)` sem 4º
argumento (`hybrid/main.py:111`) ⇒ `normalize=True` ⇒ `cv2.normalize(...,NORM_MINMAX)`
per-arquivo (`image_io.py:138`); estes arquivos viram `filtered_dir`
(`hybrid/main.py:112,115`) e são relidos em `multifocus/main.py:96` para a medida de foco
inter-plano. Compare com `hybrid/main.py:160` (`normalize=False` para preservar relações
cross-luz). `calculate_avarage_of_images` devolve uint8 (entrada uint8) — ver "Verificado".

**Sugestão de correção:** salvar as médias com `normalize=False` (e idealmente em FNI/16-bit
para não quantizar); ou alimentar o multifocus com as médias **in-memory** sem passar por
PNG. NÃO aplicar.

**Correção parcial (cross-ref MF-12, 2026-06-05):** o stretch min-max per-plano saiu do CAMINHO DE DADOS para as médias: `hybrid/main.py` agora passa as médias float via `parameters["filtered_images"]`, saltando o round-trip PNG no multifocus. O PNG continua sendo gravado para **visualização** com `normalize=True` — logo IO-05 não está totalmente resolvido (PNGs de visualização ainda sofrem stretch; a tabela de call-sites em IO-04 continua válida), mas deixou de afetar o resultado científico para as médias. O `save_image` normalize default permanece para todos os outros call-sites.

## Verificado sem achado

- **Round-trip de indexação (semântica de `y`) Python↔C confere — alimenta CONV-3.** O loop
  do writer escreve as linhas `y` na ordem `0..ny-1` (`image_io.py:171`), cada uma com pixels
  `x=0..nx-1` (`:173-178`), e o reader mapeia `image_array[y,x]=val` (`:239,241`). A auditoria
  de integração (`03-integration.md`, entrada "Indexação `float_image`...") já concluiu, por
  inspeção do FNI escrito **pelo C** (`teste_*-end-Z.fni`: `0 0`,`1 0`,…,`0 1`,…), que C e
  Python concordam na **indexação** row-major com `y=0` primeiro — o round-trip FNI **preserva
  o array** sem flip vertical. **Confirmo pelo lado Python**: o writer não inverte y (escreve
  `image_array[y,x]` na linha rotulada `y`), o reader reconstrói no mesmo `[y,x]` — não há
  espelhamento. O que permanece aberto é apenas o **sinal físico** de dZ/dY (se `y=0` é topo
  ou base da cena), que o teste de rampa/bump da Fase 3 (Task 9) decide — registrado como
  suspeita-de-convenção em CONV-3, não como bug de IO. **Verificado (teste executável):**
  `tests/test_fni_roundtrip.py::test_roundtrip_2d` (array assimétrico 5×9 — transposição
  quebraria o shape; flip quebraria os valores) e `::test_roundtrip_3channel` (4×6×3) — 4
  passed em 0.36 s (2026-06-04).
- **Header/metadados do FNI parseados corretamente.** O reader valida o header
  `begin float_image_t` (`image_io.py:199-200`), lê `NC/NX/NY` de linhas com `=`
  (`:208-210`), levanta se algum metadado faltar (`:216-217`) e se `NC<1` (`:219-220`); a
  ordem de NC/NX/NY no arquivo não importa (dict). O writer emite os quatro campos na ordem
  fixa e o rodapé `end float_image_t` (`:166-181`). Contrato de cabeçalho consistente.
- **`float("nan")` aceita o texto `nan`/`+nan` no parser Python.** O reader faz
  `list(map(float, parts[2:]))` (`image_io.py:235`); `float("+nan")`/`float("nan")` em CPython
  devolve `NaN` sem erro (verificado). Logo um FNI com `+nan` (como o writer produz para
  componentes NaN, ver INT-03) é **lido de volta como NaN** pelo Python, fechando o lado
  Python do round-trip de NaN. (A aceitação pelo **parser C** — dependente de libc/locale — é
  o que INT-03 deixa para o teste da Task 8; aqui só confirmo o lado Python.)
  **Verificado (teste executável):** `tests/test_fni_roundtrip.py::test_nan_handling_documented`
  — NaN sobreviveu ao round-trip `float64→texto+nan→float32`; 4 passed em 0.36 s (2026-06-04).
- **`normalize` (utils) tem guarda para array constante.** `normalize`
  (`utils.py:51-71`) trata `max_ == min_` devolvendo `np.zeros_like(x, dtype=np.float64)`
  (`:68-70`), evitando a divisão `0/0` que geraria NaN. A guarda está presente e correta. (A
  escolha de devolver **zeros** para um array constante é uma convenção razoável; não há

- **`convert_to_grayscale` lida corretamente com float64 via cast a float32.**
  `cv2.cvtColor(COLOR_BGR2GRAY)` **rejeita** float64 (verificado: "Unsupported depth ... CV_64F"),

  (`0.299R+0.587G+0.114B`; verificado: gray de B=0,G=0,R=255 ⇒ 76.24 ≈ 0.299·255), corretos
  para BGR. (PS-09 cobre o crash com entrada **mono** — não duplicado aqui; o caminho float64

- **`calculate_avarage_of_images` soma em float32 — sem overflow de uint8.** A média é
  calculada sobre `images_float = [image.astype(np.float32) ...]` e `np.mean(..., axis=0)`
